# A complete evaluation, without a live call

[← Project overview](../README.md) · [Architecture](architecture.md)

This example uses the repository's existing synthetic fixture and the **real service code with an injected mock provider**. It is not output from a live Jev request, an accuracy benchmark, or the historical production smoke test. The timestamp, usage, request ID, and model values below are fixed demonstration data.

## The question

A fictional support ticket mentions a duplicate charge. We want three distinct signals:

- Impact against a three-level rubric.
- A category, with an explicit uncertain fallback.
- Whether a refund is explicitly requested.

The fixture values are chosen to test interpretation and review flags; they are not an endorsement of a model judgment about the text.

## Request: tool arguments

Pass this object as `jev_evaluate` arguments in a separately authorized live setup, or use the offline replay below. **The offline path is sufficient to reproduce this page.**

```json
{
  "state": "Synthetic: A fictional support ticket asks about a duplicate charge.",
  "questions": {
    "severity": {
      "type": "score",
      "instructions": "Rate impact.",
      "criteria": [
        "Low",
        "Medium",
        "High"
      ]
    },
    "category": {
      "type": "choice",
      "instructions": "Choose category.",
      "criteria": {
        "billing": "Payment issue",
        "uncertain": "Insufficient information"
      }
    },
    "refund": {
      "type": "noul",
      "instructions": "Does it request a refund?",
      "criteria": {
        "true": "Explicit request",
        "false": "No request"
      }
    }
  },
  "sources": [
    {
      "title": "Synthetic fixture",
      "url": "https://example.invalid/fixture"
    }
  ]
}
```

For an MCP client, these arguments belong under `params.arguments` in a `tools/call` request with `params.name: "jev_evaluate"`. The adapter accepts standard object-valued `_meta` separately from arguments. Tool arguments do not accept identity or API-key fields.

## Replay it without a key

Run from the repository root on Node 22.13+; no dependency installation is needed for this core-only example:

```bash
node --experimental-strip-types --input-type=module <<'JS'
import { createJev } from './src/service.ts';
import { input, provider } from './tests/fixtures.mjs';

const service = createJev(
  { apiKey: 'mock-only', ownerId: 'fixture-owner' },
  'fixture-owner',
  {
    fetch: async () => new Response(JSON.stringify(provider())),
    now: () => new Date('2026-10-25T12:00:00Z'),
    requestId: () => 'offline-example'
  }
);

console.log(JSON.stringify(await service.evaluate(input()), null, 2));
JS
```

The `fetch` dependency above is a local function that returns a fixture. It never calls the network. Both identity and key values are invented test strings; **do not substitute real credentials into this command**. In production, gateway identity and runtime bindings—not this harness—supply those values.

## Read the result correctly

| Field | Meaning | Common mistake |
| --- | --- | --- |
| `raw_score: 1.5`, `raw_range: [0, 2]` | Position on the supplied Low/Medium/High rubric | Treating a rubric score as a probability |
| `score_100: 75` | `100 × 1.5 / 2` | Reading it as 75% accuracy |
| Score `confidence: 0.69` | Separate fixture-provided confidence | Treating it as independent fact verification |
| `choice: "billing"` | Selected category from the supplied labels | Assuming the ticket or charge was verified |
| `yes_probability: 0.5`, `confidence: null` | Noul's yes estimate; no extra confidence invented | Replacing null with fabricated certainty |
| Overall `needs_review: true` | At least one answer triggered a provisional threshold | Assuming the app opened a review task |
| `sources[].verification_status: "unverified"` | Caller-supplied metadata echoed unchanged apart from label | Assuming the URL was visited or used as evidence |
| `request_id: "offline-example"` | Locally generated correlation value (fixed here) | Treating it as a provider trace ID |

The fixture's probabilities and confidence are separate supplied values. Do not reconstruct one from the other or interpret either as measured correctness.

## Failure is a different result

Authorization and configuration checks happen before a provider attempt. A live provider failure is not converted into an answer. For example, a busy response produces an MCP tool result with `isError: true` and an error code such as `PROVIDER_BUSY` inside its text content. The integration does not retry automatically.

See [`tests/service.test.mjs`](../tests/service.test.mjs) for no-network authorization failures, response caps, timeout behavior, and redacted provider errors. [`tests/domain.test.mjs`](../tests/domain.test.mjs) exercises the review thresholds and malformed output cases.
